# emu 설계 문서 (Design Invariants)

이 문서는 emu의 **불변식(invariants)** — 최초 설계에서 확정됐고 이후 변경이 넘어서는 안 되는
선 — 을 한 곳에 못 박는다. 새 기능이 이 선을 넘는다면 그것은 기능 추가가 아니라 **다른 도구**다.

> 출처: 최초 설계는 첫 커밋 `09fb474` 와 초기 README에 서술됐다. 진행 항목·의사결정 로그는
> [`BACKLOG.md`](BACKLOG.md), 사용자 문서는 [`../README.md`](../README.md) / [`../README.ko.md`](../README.ko.md).

---

## 1. 정체성 (무엇이고, 무엇이 아닌가)

**emu는 IDE 없이 에이전트가 비대화형으로 모는 Flutter 개발/디버그 inner-loop 도구다.**
해자는 "IDE 없이 에이전트가 모는 루프 + 로그·변수 관찰 가능성"이다.

- **이다**: 기동 → 구동 → 검증 루프를 단발성 CLI 호출로 닫는 드라이버.
- **아니다**: DevTools/IDE의 대체재, e2e 프레임워크(`integration_test`/`patrol`/`maestro`)의 경쟁자,
  UI 단언 엔진. 이들과 **다른 층위**이며 그 위에 로그·변수 검증을 더한다.

이 정체성이 우선순위의 1차 기준이다: **"에이전트 루프의 한 번의 호출로 판정을 강화하는가."**

## 2. 아키텍처 불변식

### I1. 엔진 하나, 프런트엔드 둘
로컬 서버가 `flutter run --machine` 세션(엔진)을 **단독 소유**하고, CLI와 웹 대시보드는
그 서버의 HTTP/WebSocket API **클라이언트**다. 엔진을 소유하는 주체는 항상 서버 하나뿐이다.

```
flutter run --machine  ◄─JSON-RPC─►  engine  ──►  server (127.0.0.1:4577)
                                                    ├─ REST + WebSocket API
                                                    ├─ web dashboard  (browser)
                                                    └─ CLI            (terminal / agent)
```

### I2. 데몬 프로토콜로 제어한다 — 키 전송 금지
제어는 Flutter 데몬 프로토콜(`app.restart` 의 `fullRestart` 토글 등)로 수행한다.
**tmux·키 입력 시뮬레이션·터미널 스크래핑을 쓰지 않는다.** 상태는 프로토콜 이벤트로 관측한다.

### I3. 자급형 단일 바이너리
대시보드 자산(`web/`)을 `bundle_web.dart` 로 바이너리에 임베드해 `build.sh` 가 단일 실행 파일을
만든다. 런타임에 외부 자산 서버·CDN·별도 데몬을 요구하지 않는다.

### I4. 무상태 · 단발성 명령 모델
모든 명령은 시작하고, 판정하고, 끝난다. 앱을 **명령 사이에 멈춰 두지 않는다**(그러면 로그·probe가
멎는다). `probe`/`inspect` 조차 스냅샷을 찍고 **즉시 resume**한다. 대화형 `break`/`step` 을
의도적으로 넣지 않은 이유가 이 불변식이다.

### I5. 에이전트 우선 인터페이스
모든 명령에 `--json` 이 있고, 종료코드로 판정한다. `up`/`reload`/`restart` 는 **최종 상태 + 직후
에러**를 한 번에 반환한다(verdict). 사람의 눈·손을 전제하지 않는다.

**관측 프리미티브** — 에이전트가 "지금 무엇을 해도 되는가"를 눈치(`sleep`)가 아니라 판정으로 알게
하는 신호들. 두 개가 있다:
- **first-frame**(`up`): 앱이 실제로 화면을 그렸는가 = **탭 가능한가**. 그리기 전 입력은 유실된다.
- **settle**(`tap`/`swipe`/`shot` 기본 동작, `settle.dart`): 리빌드·라우트 전환·애니메이션이
  가라앉았는가 = **결과를 관찰할 준비가 됐는가**. 탭 직후 shot이 로딩·전환 중간 프레임을 찍는 함정을
  막는다. 조회 가능한 서비스 확장이 없어 `SchedulerBinding` 을 VM Service로 폴링해 판정한다.

둘 다 "눈치껏 기다리기"를 결정적 신호로 대체한다. 새 구동 동작을 추가할 때는 대응하는 관측
프리미티브가 있는지 먼저 묻는다(없으면 에이전트가 `sleep` 로 때우게 되고, 그건 이 불변식 위반이다).

## 3. 경계 불변식 (emu가 하지 않는 것)

### B1. UI 단언을 하지 않는다 — 조회는 하되 판정은 하지 않는다
2026-07 초 설계 당시엔 "위젯 트리를 질의하지 않는다"였다. 이후 `emu tap --text/--key`와
`emu find --text/--key/--type`(`lib/src/locate.dart`)가 VM Service `evaluate`로 온디바이스
`Element` 트리를 실제로 순회·질의하게 되면서 이 경계는 **넓어졌다** — 좌표만 주입하던 것에서
셀렉터(라벨/키/타입)로 위젯을 **조회**하는 것까지가 emu의 영역이 됐다. 근거: 실사용
피드백(GitHub Issue #2)에서 "레이아웃이 조금만 바뀌어도 좌표가 깨진다", "스크린샷 배율 환산
실수가 잦다"는 문제가 반복됐고, 좌표 산출이라는 우회 경로 자체를 없애는 게 B3(물리 픽셀
좌표계)를 대체하는 게 아니라 그 앞 단계(좌표를 어떻게 얻는가)를 강화하는 방향이었다.

**여전히 진실인 부분** — 넓어지지 않은 경계: **emu는 조회 결과에 대한 판정(pass/fail 단언)을
하지 않는다.** `find`가 0개를 찾아도 에러가 아니라 `(no match)`를 정상 종료코드로 반환한다 —
"이 버튼이 있어야 한다/없어야 한다"를 정하는 건 여전히 호출자(에이전트)다. e2e 프레임워크의
`expect(find.text('X'), findsOneWidget)`류 단언 API는 emu에 없고 앞으로도 없다. "이 화면이
올바른 상태인가"의 **판단은 에이전트**(스크린샷 + 조회 결과)가, **검증은 `assert`(로그)/
`probe`(변수)** 가 한다는 원래 구도는 그대로다. 셀렉터 기반 UI *단언*이 필요하면 e2e 프레임워크를
쓰고 emu는 그 위에 로그·변수 검증을 더한다는 것도 변하지 않았다 — 달라진 건 셀렉터 기반 UI
*조회*까지는 emu 안으로 들어왔다는 것뿐이다.

### B2. Flutter 위젯 한정
입력은 프레임워크 레벨(VM Service 합성 이벤트 / `updateEditingValue`)이라 네이티브 뷰·웹뷰
텍스트 필드엔 닿지 않는다. emu의 대상은 Flutter 앱이므로 이는 타협이 아니라 범위 정의다.

### B3. 좌표계는 물리 픽셀 하나
사용자·에이전트에게 노출하는 좌표는 **물리 픽셀**뿐이다(`shot` 이 캡처하는 공간). 논리 좌표 변환은
백엔드가 dpr로 내부 처리한다. 플랫폼(Android/iOS)이 달라도 좌표 규약은 동일하다.

### B4. 학습 메모리는 권위가 아니다
`.emu/memory.json` 의 학습값(dpr·화면크기 등)은 재계산 재료일 뿐, 다음 실행이 이걸 믿고
스크린샷 없이 탭하지 않는다. **좌표는 부팅마다 썩으므로 저장하지 않는다.** 설정도 "머신·시간을
넘어 참인가"라는 커밋 경계로 계층화한다(참이면 `emu.yaml` commit, 지금만 참이면 `emu.local.yaml`).

### B5. 대시보드 페이지의 명령은 설정에만 있다 — 커스텀 화면은 묻고, 대시보드가 답한다

`emu.yaml` 의 `pages:` 는 프로젝트 명령을 대시보드에 붙이지만, 요청은 **id 만** 고르고 명령은 싣지
못한다. 요청이 싣는 값(고른 행, 입력)은 `[program, arg, …]` 의 한 인자 안에만 들어간다. `confirm: true`
명령은 서버가 428 로 실제 명령 줄을 돌려주고, 확인은 그 줄을 본 사람만 보낼 수 있다.

`html` 블록(커스텀 화면)은 opaque origin·네트워크 없는 sandbox frame 이라 대시보드 DOM·세션 토큰을
보지 못한다. 대시보드 인터페이스(`window.emu`, #49)는 이 경계를 넓히지 않는다:

- frame 은 **블록에 선언된 id 만** 실행하고, `input` 은 `inputs:` 에 적은 이름만 간다.
- 확인·입력 창은 **대시보드가 frame 바깥에** 그린다(frame 이 스스로 누를 수 없게). 머리에 출처
  (블록 제목·`src`)를 박고, 글자는 텍스트로만 넣는다. 한 번에 한 창, 화면에 있는 frame 만(보이는 페이지의, 접히지 않은).
- `emu.confirm` 은 화면의 UX 일 뿐 서버 확인을 대신하지 않는다 — frame 은 `confirmed` 를 보낼 수 없고,
  `confirm:` 액션은 대시보드 자체 확인 창(실제 명령 줄)을 거친다.
- 확인 창을 합칠 때도 이 순서는 그대로다. 화면의 설명은 `emu.run(id, {confirm})` 으로 **실행 요청에 실려**
  와 실제 명령과 한 창에 보인다. `emu.confirm` 은 답을 받아야 다음 실행이 오므로 미리 합칠 수 없다 —
  화면에 답하지 않은 「예」를 먼저 돌려주면 frame 이 그것으로 다른 일을 할 수 있다. 그래서 OK 뒤 창을
  잠깐(1초) 붙잡아 두고, 그 사이 같은 화면의 `confirm:` 실행이 오면 같은 창에서 명령을 이어 묻는다.
  그 밖의 경우는 두 번 묻는다(안전한 쪽).
- 연달아 취소되는 화면은 사용자가 막을 수 있다(새로고침 전까지 바로 아니오).
- `emu.select`·`emu.refresh` 는 그 화면의 페이지 안에서만 — 페이지 list 에 있는 행만 고르고, 블록은 받는
  중이거나 1초 안이면 다시 받지 않는다(onData 에서 refresh 하는 화면이 명령을 끝없이 돌리지 않게).

실행 중인 명령이 묻는 것(`interactive: true` 의 `::emu-ask` 줄)도 같은 경계 안에 있다:

- 묻는 것은 **이미 설정에 있는 명령**이다. 질문은 그 명령의 stdin 에 답 한 줄을 돌려줄 뿐 무엇도 실행하지
  않고, 답은 질문에 맞춰 거른다(confirm 은 bool, prompt 는 그 질문의 칸, choose 는 그 질문의 항목).
- **시작한 곳에만** 묻는다. 실행 요청은 `asker`(탭·`emu run` 마다 새 id)를 싣고, 그 id 로
  `/api/stream?asker=` 에 붙은 소켓에만 질문을 보낸다 — 다른 탭에 뜨거나 broadcast 되지 않는다. 답은
  `askId`(서버가 만든 난수)로만 받는다.
- 창은 대시보드 창 규칙 그대로(텍스트로만, 출처 = 페이지·액션 이름, 한 번에 한 창, danger 면 Cancel).
  실제 명령은 버튼을 누를 때(필요하면 `confirm:`) 이미 보였으므로 다시 보이지 않는다.
- 크기 상한: 줄 64 KB, title 200·message 2000·detail 20000 자, 항목 200개·칸 12개.
- `interactive` 가 없는 명령의 그런 줄은 출력일 뿐이다(우연히 찍힌 줄로 창이 뜨지 않게).
- **답할 곳이 없거나 시간이 지나면 `null`** — 도구는 「묻지 못하면 멈춘다」로 짜면 emu 없이 돌 때와 같다.
  `EMU_ASK=1` 은 답할 사람이 있다는 뜻이다(없으면 `0`).
- 실행 `timeout:` 은 질문이 답을 기다리는 동안 멈춘다 — 사람을 기다린 시간 때문에 명령이 죽지 않게,
  그러면서도 명령 자신이 쓴 시간은 그대로 상한을 받는다. 질문 하나는 `askTimeout`(기본 120초)까지만 기다린다.

`auto:` 액션은 서버가 파일 변경에 스스로 실행하지만, 경계는 같다: 실행하는 것은 설정의 명령 그대로이고(채울 값이
없어 `{{…}}` 를 쓰면 설정 오류), `confirm` 액션은 대상이 아니다. 요청이 바꿀 수 있는 것은 스위치(on/off)뿐이다.

| 대시보드 확인 창 `confirm:` 맵 — 설명·강조·preview 를 더해도 실행할 명령은 늘 보인다 | I1(대시보드·`emu run` 이 같은 428 응답), I5(실행 전 관측) | ✅ |
| 디바이스 임대 — 한 기기 = 한 서버, 프로젝트·worktree 간에도([`DEVICE_LEASE.md`](DEVICE_LEASE.md)) | I1(서버가 기기까지 단독 소유), I5(섞인 입력으로 판정 오염 방지) | ✅ |
| 대시보드 페이지(`pages:`) — 프로젝트 도구를 「명령 + 출력」 블록으로, `emu run`·`emu block` 으로도 | I1(대시보드·CLI 같은 API), B5 | ✅ |
| 커스텀 화면 인터페이스(`window.emu`) — 값·결과 주고받기, 대시보드가 그리는 확인·입력·선택 창, 행 고르기·다시 받기, 확인 창 합치기 | B5 | ✅ 1·2단계(#49) |
| 실행 중에 묻기(`interactive: true`, `::emu-ask`) — 실행을 시작한 탭·터미널에만, 답할 곳 없으면 `null`, 기다리는 동안 timeout 정지 | B5, I1(대시보드·`emu run` 같은 API) | ✅ 3단계(#49) |

보류 항목(전부 근거 있는 보류)도 불변식으로 설명된다:
- 🚫 `emu e2e`(외부 e2e 엔진 구동) — 입력 수단 확보로 전제 소멸(B1과 중복).
- 🚫 대화형 `break`/`step`/`continue` — **I4(무상태·단발성)와 정면충돌**.
- 🚫 비-Flutter 텍스트 입력 — **B2(Flutter 한정)** 밖 + 견고·무의존 경로 없음.
- 🚫 `emu routes`(네비게이션 스택 덤프) — 공개 API로는 전체 스택을 못 얻고 Flutter의 private
  Navigator 내부 구현(`_ModalScope` 등, 릴리스마다 리팩터링 대상)에 기대야 한다. I1~I5/B1~B4를
  직접 어기진 않지만, 버전 fragility가 커서 capability-probe(런타임에 존재를 직접 확인하고 실패
  시 정직하게 보고) 설계로 재검토 중 — BACKLOG 참고.

## 5. 변경 판단 기준

새 기능을 검토할 때 이 질문을 통과해야 한다:

1. **I1~I5 중 하나라도 깨는가?** 깨면 그건 emu가 아니라 다른 도구다. 재설계로 취급한다.
2. **B1~B4의 경계를 넘는가?** 넘으면 범위 확장이므로 명시적 근거와 함께 이 문서를 갱신한다.
3. **에이전트 루프의 "한 번의 호출로 판정"을 강화하는가?** 아니면 우선순위가 낮다.
4. **실수요가 있는가, 투기인가?** 투기면 근거를 남기고 보류한다(BACKLOG의 보류 패턴).
