# emu report — emu 에 리포트 보내기

emu 를 쓰다 생긴 **emu 자체의** 문제·바람을 emu 저장소에 이슈로 보낸다. 사용자의 앱 버그는 대상이 아니다.
모든 일은 `emu report` CLI 가 한다 — 본문을 손으로 만들거나 `gh` 를 직접 부르지 않는다.

## 보내기

1. **알린다.** 공개 저장소 github.com/HuanSuh/emu 에 **공개 이슈**로 올라간다는 것.
2. **종류**를 묻는다: `bug` · `feature` · `question`. 대화 맥락으로 짐작되면 그것을 먼저 권한다.
3. **제목**(한 줄)과 **내용**을 받는다. 버그면 재현 단계·기대·실제를 권한다. 이 대화에서 emu 가 실제로
   실패한 장면(명령·오류)이 있으면 그것으로 초안을 제안할 수 있지만, 사용자의 앱·회사·업무 이야기는
   넣지 않는다. 파일 내용을 읽어 붙이지 않는다.
4. **첨부**를 고르게 한다. 기본은 아무것도 없음:
   - `logs[:N]` — 지금 세션의 최근 N줄(기본 200)
   - `errors` — 최근 예외 배너
   - `shot` — 지금 화면(세션이 떠 있어야 함; 이슈를 만든 뒤 코멘트에 붙여 넣음)
   - 파일 경로 — 사용자가 직접 고른 파일만
5. **미리 보기** — 내용은 임시 파일로 넘긴다(따옴표·줄바꿈이 셸에서 깨지지 않게):

   ```bash
   cat > "$TMPDIR/emu-report-body.md" <<'EMU_REPORT_EOF'
   <내용>
   EMU_REPORT_EOF
   emu report <kind> "<제목>" --body-file "$TMPDIR/emu-report-body.md" [--attach …]... --dry-run
   ```

   출력(대상·제목·라벨·본문·`!` 안내)을 **고치거나 줄이지 말고 코드 블록 그대로** 보여 준다. 경로·이름·토큰은
   이미 가려져 있다 — 그래도 남은 민감한 것이 있는지 사용자에게 확인하게 한다. 마지막 줄의
   `draft <id>` 를 기억한다. 그리고 묻는다: **보낼까요 / 고칠까요 / 그만둘까요**.
6. 사용자가 **분명히 보내라고 답했을 때만** `emu report --send <id>` 를 실행한다. 고치면 4–5 를 다시 한다
   (새 draft id). "보냈다"고 말하는 건 `✓ sent — #<n> <url>` 이 출력됐을 때뿐이다.
   - `gh` 가 로그인돼 있지 않으면 미리 채운 GitHub 작성 화면이 브라우저로 열린다 → "브라우저에서 제출해
     주세요" 라고 안내한다(아직 보내진 게 아니다).
   - 스크린샷이 있으면 출력대로 안내한다(클립보드에 있으니 이슈 코멘트에 ⌘V).
   - `! already sent a moment ago` 면 새로 만들지 않은 것 — 앞서 만든 이슈 주소를 알려 준다.
   - `✗ …` 면 그 문구를 그대로 보여 준다(예: `gh auth login --hostname github.com` 안내).

## 내 리포트

`emu report --mine` 결과를 그대로 보여 준다: `#번호 [상태] 제목 (코멘트 수) PR #…` 와 주소.
상태는 `open` · `fixing`(연결된 PR 있음) · `fixed` · `closed` · `not planned`. gh 가 없으면 GitHub 에서 볼 수 있는
주소가 나온다.

## 규칙

- 확인 없이 보내지 않는다. `--yes` 는 쓰지 않는다 — 보내는 것은 언제나 사용자가 본 draft 의 `--send <id>` 다.
- 미리 보기 내용을 요약·편집해서 보여 주지 않는다. 보이는 것이 보내지는 것이다.
- 사용자가 고르지 않은 첨부를 넣지 않는다.
